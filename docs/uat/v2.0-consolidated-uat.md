# UAT book: ProbeMatrix Learnings Coach v2.0, consolidated (Phases 3 to 7)

**Build under test: v2.0.0-rc.N (`pmlc 2.0.0rcN`).** Replace `N` with the release-candidate number you were given, for example `v2.0.0-rc.1` and `pmlc 2.0.0rc1`.

User acceptance testing (UAT) for v2.0, run once at the end, in the Claude app. Phases 3 to 7 are not tested one by one: each phase adds its own section to this book, and you run the whole book on the release candidate. A fix goes into the next release candidate (`rc.N+1`), and you re-run only the failed tests on it.

Every test tells you:
- what to paste;
- which file to attach;
- what you should see.

**Where the numbers come from.** Each phase's numbers come from a real run of the engine when that phase was finished. The Phase 3 numbers come from a run on 2026-10-20, on the inputs listed under Setup. That run printed `2.0.0a4`: the version number is raised only at release time, and nothing else changes with it. So wherever this book shows a version, you should see your release candidate's (`2.0.0rcN`, or `v2.0.0rcN` in page footers). If you are testing the Phase 3 alpha early, it is `v2.0.0-alpha.5` (`pmlc 2.0.0a5`).

Where a test depends on the agent's own writing or behaviour, it is a checklist, not exact text.

**Words used in this book.** Phase 2's words still apply: engine, export, finding, evidence item, workspace, pack, register, language check, sign-off, forced draft, DRAFT ribbon, embed mode and shared copy. The Phase 2 book (`docs/uat/v2.0-phase-2-uat.md`) explains each one. New in Phase 3:
- **Hub:** the `learnings-coach` skill, where every request starts. It sets up the workspace, works out what you want, shows a numbered plan, and waits for your OK.
- **Plan:** the numbered list of steps for a request, made by the engine's `plan` command from a **preset** (a ready-made workflow, such as `leadership`) or from the audiences or skills you name. Each step is **done**, **todo**, or **planned** (it belongs to a later phase and is skipped).
- **Gate:** the check a step must pass before the next one starts. For a pack it is `check-pack --strict`; for the register, `check-register --strict`; for a pack meant for outside the organisation, also an approved review by a person.
- **Strict mode** (`--strict`): some checks only warn by default; strict mode makes them fail.
- **LR-nn:** the id of one learning in the register, such as `LR-08`. A pack item that carries a register learning names it (`"learning": "LR-08"`), and the page shows it as a **Learning LR-08** button.
- **Organisation files:** files your organisation fills in, never the agent: `adoption.csv` (did you accept each learning), `distribution.csv` (who each pack reached) and `verification.jsonl` (did each learning stick). The engine writes them blank, and never overwrites one.
- **Comparator:** the numbered items (observations, root causes, recommendations, actions) of another report on the same event, written as `comparator.json`, with a map of which learning matches which item.
- **Run manifest:** a small record beside the workspace (`run-manifest.json`) of what the run is for, its jurisdiction and its retention review date.
- **Purge:** deleting a run's working data after its retention date, while keeping the run manifest.

## Before you start

> - **Do a 5-minute dry run first:** P3-A1 and P3-B1 in conversation 1. If either fails, stop and report it before running the rest of the book.
> - **If the agent cannot write next to the uploaded file** (the upload folder is read-only), say: "Use `--root` with a writable working folder." The run is then made inside that folder. This is not a failure.
> - **The agent works on copies.** Uploaded files cannot be changed. So a prompt that changes a file asks the agent to copy it into the run's `outputs` folder (or the workspace) first and to work on that copy.
> - **Ask for the files.** When a test produces an output, ask: "Give me the output files to download." Open HTML pages in your browser, and `.xlsx` and `.csv` files in Excel.
> - **Never sign off for the agent's sake.** Only P3-I3 and P3-I5 tell the agent you reviewed a file. In P3-I3 the claim is deliberate: Hazira is forced draft, so the engine must still refuse. In every other test, do not say you reviewed anything.
> - **Usage limits.** The book needs 7 conversations. If you hit the app's usage limit, that is not a failure: stop, and carry on in the same conversation when the limit resets.

**How to read "Expected".**
- Exact text in `code` should appear word for word in the agent's reply or in the engine output it shows you.
- If the agent only summarises, ask: "Show me the engine's exact output."
- Long paths are left out; only the end of each line matters. `…` stands for the part of a path or line left out.
- A date written as `<today>` is the day you run the test, as `YYYY-MM-DD`.
- "Exit code" is the number the engine ends with: 0 means OK, 1 means problems found or refused. Ask the agent for it if it does not say.

**What the engine commands do.** You do not need to type them: each prompt asks the agent to run them. For reference, the Phase 3 commands are `setup` (the first six steps in one go), `plan`, `facts`, `register-md`, `templates`, `export-actions`, `compare`, `index`, `run-manifest` and `purge`, and the new `--strict` and `--register` options of `check-pack` and `check-register`. The user manual describes each one in `docs/manual/commands/` (repository only).

## Severity guide

| Severity | Meaning | Examples |
|---|---|---|
| **Blocker** | Wrong or unsafe output | a crash; a number that differs from this book; a learning with no citation; a personal name or a blame word in an output; the agent signs off by itself, or writes an owner, a due date or an organisation's response; an organisation file overwritten or blanked; purge deleting without `--yes` or outside a run folder; a shared copy that shows a name, a company, a tag, a time or a full date; sign-off accepted on Hazira |
| **Major** | A feature does not work, but there is a workaround | the hub runs steps before your OK, or asks several questions at once; a skill does not start, but naming it works; a pack fails `check-pack --strict` and the agent fixes it on request; a manual page is missing |
| **Minor** | Wording or layout | an awkward heading; a hint that is hard to follow; a table that wraps badly on a phone; a confusing but harmless profile flag |

## Recording results

1. Make a copy of this file, or print it, and tick Pass or Fail for each test. Write the release candidate you tested (for example `v2.0.0-rc.1`) at the top. Add a note for every Fail, and for anything that surprised you.
2. When you finish, post a short summary as a comment on issue #1:
   - the release candidate tested;
   - the number passed and failed in each phase section;
   - the IDs of the failures;
   - the severity of each failure.
3. Open each failure as its own GitHub issue with the label `v2.0`, and start its title with "UAT" and the test ID (for example "UAT P3-D3: adoption.csv rejected after saving in Excel"). Include:
   - the test ID and the release candidate;
   - the prompt;
   - what you expected;
   - what you saw (paste the agent's reply, or attach a screenshot).

**What happens next**
- **All pass, or only Minor findings:** UAT is accepted. Minors are fixed or listed as known issues, and v2.0 goes to `main` through the single pull request ("Closes #1"), followed by the `v2.0.0` tag and release.
- **Any Major or Blocker:** the fix is made on the feature branch and released as the next candidate, `v2.0.0-rc.N+1`. Pin the new tag as in Setup step 1, then re-run the failed tests and every test in the same section. Nothing reaches `main` until the book passes, so there is nothing to revert.
