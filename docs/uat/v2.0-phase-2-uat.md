# UAT book: ProbeMatrix Learnings Coach v2.0, Phase 2

**Build under test: v2.0.0-alpha.4 (`pmlc 2.0.0a4`).**

User acceptance testing (UAT) for the second v2.0 alpha, run in the Claude app or on claude.ai. Phase 2 adds the trust gates: a language check, a review and sign-off step, smaller pages that embed only what they cite, rules for sharing outside the organisation, and privacy tools. It also adds the user manual. Every test tells you:
- what to paste;
- which file to attach;
- what you should see.

Every number below comes from a real run of the engine on 2026-10-19, on the inputs listed under Setup. That run printed `2.0.0a3`, because the version number is raised to `2.0.0a4` just before the release; nothing else changes with it. Where a test depends on the agent's own writing (sections G and H), it is a checklist, not exact text.

**Words used in this book**
- **Engine:** the small Python program (`pmlc.py`) that the skills run to count, filter and check. The agent runs it for you.
- **Export:** the `.xlsx` file you download from ProbeMatrix for one investigation.
- **Finding:** one row of the export, such as `FND-0001`. **Evidence item:** one piece of evidence, such as `EVD-0001`.
- **Workspace:** the folder of files the engine builds from one export. Outputs go in an `outputs` folder beside it.
- **Pack:** one learning output (a board brief, a set of learning cards), written as a JSON file and turned into an HTML page and a Markdown file.
- **Register:** a lessons-learned register, one row per learning, as a JSON file and an Excel workbook.
- **Language check:** the engine's check of the wording of a pack or register. It has twelve rules, JC1 to JC12 (for example JC1 personal names, JC2 blame or punishment words, JC6 retraining as the only fix, JC8 numbers with no source). An **error** fails the check; a **warning** does not.
- **Sign-off:** a person's record that they reviewed a pack or register. It writes a `handling` block into the file: the status (`draft`, `reviewed` or `approved`), the reviewer's role (never a name), the date, the classification, the legal review and a fingerprint of the content (`content_hash`).
- **Forced draft:** nothing can be signed off while the investigation is still in progress in ProbeMatrix, or while no finding has been edited by a person. The Hazira sample is both, so it always stays draft.
- **DRAFT ribbon:** the "DRAFT" banner at the top of every page that is not approved.
- **Embed mode:** how much of the investigation a page carries inside it. `cited` (the default) carries only the records the pack cites; `summary` also leaves out evidence descriptions and quotes; `full` carries everything relevant, as Phase 1 did.
- **Shared copy:** a masked copy for outside the organisation (`--share external` or `--share public`), written as `<name>.external.html`.

## Before you start

> - **Do a 5-minute dry run first:** A1 (conversation 1), then B1 (conversation 2). If either fails, stop and report it before running the whole book.
> - **If the agent cannot write next to the uploaded file** (the upload folder is read-only), say: "Ingest with `--root` pointing to a writable working folder." The workspace is then made inside that folder. This is not a failure.
> - **The agent works on copies.** Uploaded files cannot be changed, and sign-off writes into the file. So every prompt that changes a pack or register asks the agent to copy it into the run's `outputs` folder first and to work on that copy.
> - **Ask for the files.** When a test produces an output, ask: "Give me the output files (the HTML and the Markdown) to download." Open the HTML in your browser. For the print test (D3) use Chrome or Edge.
> - **Never sign off for the agent's sake.** Only C3, E1, E2 and E3 tell the agent you reviewed a file. In every other test, do not say you reviewed anything.
> - **Usage limits.** The book needs 6 conversations. If you hit the app's usage limit, that is not a failure: stop, and carry on in the same conversation when the limit resets.

**How to read "Expected".**
- Exact text in `code` should appear word for word in the agent's reply or in the engine output it shows you.
- If the agent only summarises, ask: "Show me the engine's exact output."
- Long paths are left out; only the end of each line matters. `…` stands for the part of a path left out.
- A date written as `<today>` is the day you run the test, as `YYYY-MM-DD`; `<this month>` is its month and year, such as `October 2026`.

## Appendix: putting `main` back to the Phase 1 alpha (revert procedure)

This is done only on the owner's call, by whoever maintains the repository. It never rewrites public history. **`main` is never force-pushed.** The result is `main` at version `2.0.0a5` (`v2.0.0-alpha.5`), whose files are the same as `v2.0.0-alpha.3` (the Phase 1 alpha) apart from the version number.

The version number always moves forward. The app decides whether to refresh its copy from the version number, so putting back `2.0.0a3` would leave anyone who already updated stuck on the Phase 2 alpha.

It assumes the interim merge was a true merge commit (not squash, not rebase) and that nothing else has landed on `main` since. If either is not true, stop and work out a plan first.

1. **Make the undo.** Start with `git fetch origin`. Then start a new branch from the current `main` and revert the alpha's merge commit, keeping the first parent: `git switch -c revert/v2.0-alpha.4 origin/main`, then `git revert -m 1 <merge SHA, posted on issue #1> --no-edit`. The files on the branch are then exactly what `main` held before the merge: commit `ff493f2`, whose tree equals tag `v2.0.0-alpha.3`. Check it: `git diff ff493f2 HEAD` prints nothing.
2. **Move the version forward.** Run `python3 tools/release.py 2.0.0a5`. It sets `2.0.0a5` in `skills/learnings-coach/scripts/pmlc.py` and `2.0.0-alpha.5` in both plugin manifests. Then regenerate the golden Markdown fixtures, which carry the version in their footer: `PMLC_UPDATE_GOLDEN=1 python -m pytest tests/test_pack.py -k golden`; read the diff, which should change only the version in each footer. Add a CHANGELOG entry `### 2.0.0a5`: "Reverts the Phase 2 alpha on main; the same as 2.0.0a3 apart from the version." Commit.
3. **Merge the undo.** Run the tests on the revert branch (`python -m pytest tests -q`); they must all pass. Push the branch and open a pull request against `main`. The automatic tests run on the pull request; wait for them to pass. Merge it with a merge commit (not squash, not rebase), and wait for the tests on `main` to pass. Tag the result `v2.0.0-alpha.5` (`git tag -a v2.0.0-alpha.5 -m "Revert Phase 2 alpha on main"`, then `git push origin v2.0.0-alpha.5`), and post a comment on issue #1.
4. **Users update.** Anyone who updates the marketplace now gets `2.0.0a5`, which behaves exactly like `2.0.0a3`. Anyone who pinned `#v0.3.5` or `#v2.0.0-alpha.3` is unaffected.
5. **Bringing Phase 2 back later.** On the feature branch, note its tip first (`git rev-parse HEAD`; call it `<feature-tip-before>`). Bring in `main` (which now contains the undo), then revert the undo commit itself (`git merge origin/main`, then `git revert <undo-commit>`). Expect conflicts on the version in `pmlc.py`, the two manifests, the golden fixtures and the CHANGELOG: keep the feature branch's version of each, then run `tools/release.py` with the next unused alpha number. Then check that `git diff <feature-tip-before> HEAD` shows only the lines you meant to change. Skipping this step would make the next merge silently drop all of Phase 2.
