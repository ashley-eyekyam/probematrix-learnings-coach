# UAT book: ProbeMatrix Learnings Coach v2.0, Phase 1

**Build under test: v2.0.0-alpha.3 (`pmlc 2.0.0a3`).**

User acceptance testing (UAT) for the v2.0 alpha, run in the Claude app or on claude.ai. Every test tells you:
- what to paste;
- which file to attach;
- what you should see.

Every number below comes from a real run of the engine on 2026-10-18 at version `2.0.0a3`. The counts in section H are indicative (see H).

**Words used in this book**
- **Engine:** the small Python program (`pmlc.py`) that the skills run to count, filter and check. The agent runs it for you.
- **Export:** the `.xlsx` file you download from ProbeMatrix for one investigation.
- **Finding:** one row of the export, such as `FND-98A4D631`. **Evidence item:** one piece of evidence, such as `EVD-5527`.
- **Workspace:** the folder of files the engine builds from one export (`findings.json`, `clusters.json` and so on). Outputs go in an `outputs` folder beside it.
- **Classify:** the step that sorts every role named in the findings into a function (for example F02 Mechanical Maintenance), a level (T1 frontline up to T5 board) and a relation (actor, approver, owner, and so on).
- **Overlay:** an optional list of extra role words for one kind of site. `india-process-site` adds Indian process-plant job titles.
- **Pack:** one learning output (a board brief, a set of learning cards), written as a JSON file and turned into an HTML page and a Markdown file.
- **check-pack / check-register:** engine checks that every citation in a pack or register points at a real finding or evidence item.

## Before you start

> - **Do a 5-minute dry run first:** A1 and B1 (conversation 1), then H1 (its own conversation). If any of them fails, stop and report it before running the whole book.
> - **If the agent cannot write next to the uploaded file** (the upload folder is read-only), say: "Ingest with `--root` pointing to a writable working folder." The workspace is then made inside that folder. This is not a failure.
> - **Ask for the files.** When a test produces an output, ask: "Give me the output files (the HTML and the Markdown) to download." Open the HTML in your browser.
> - **Usage limits.** The full book needs 30 or more conversations, so you may hit the app's usage limit. That is not a failure: stop, and carry on in the same conversation when the limit resets. To save conversations, run the five no-trigger tests (I18 to I22) one after another in a single conversation; if any of them starts the Learnings Coach, record that as the failure and run the rest in new conversations. Skip I12 when E2 has passed. Every other H and I test needs its own new conversation, because it tests which skill starts.

**How to read "Expected".**
- Exact text in `code` should appear word for word in the agent's reply or in the engine output it shows you.
- If the agent only summarises, ask: "Show me the engine's exact output."
- Long paths are left out; only the end of each line matters.
- If the agent says the workspace already exists, ask it to show you the output from when it was first made. Do not let it overwrite the workspace with `--force` unless the test says so.

- [ ] A pack is produced: an HTML page and a Markdown file in the run's `outputs` folder. The agent gives them to you to download (ask if it does not).

- [ ] The status line `Learning purposes: not a statutory document` appears near the top. The pack also says these are draft learnings, because the investigation status is `in_progress`.

## Severity guide

| Severity | Meaning | Examples |
|---|---|---|
| **Blocker** | Wrong or unsafe output | a crash; a number that differs from this book; a learning with no citation; a personal name or a blame word in an output |
| **Major** | A feature does not work, but there is a workaround | a skill does not start, but naming it works; a pack fails check-pack and the agent fixes it on request |
| **Minor** | Wording or layout | an awkward heading; a table that wraps badly on a phone |

## Recording results

1. Make a copy of this file, or print it, and tick Pass or Fail for each test. Add a note for every Fail, and for anything that surprised you.
2. When you finish, post a short summary as a comment on issue #1:
   - the number passed and failed in each section;

   - the test ID;

   - what you expected;
   - what you saw (paste the agent's reply, or attach a screenshot).

**What happens next**
- **All pass, or only Minor findings:** UAT is accepted. Minors are fixed in Phase 2.
- **Major findings that can be fixed within a day:** fixed on the branch, released as the next alpha (`v2.0.0-alpha.4`), and the failed tests are run again.
- **Any Blocker, or Major findings needing longer:** `main` becomes 0.3.6, identical to 0.3.5 (see the appendix), the fix is made on the branch, and the alpha is merged again later.

## Appendix: putting `main` back to 0.3.5 (revert procedure)

This is done only on the owner's call, by whoever maintains the repository. It never rewrites public history. **`main` is never force-pushed.** The result is `main` at 0.3.6, identical to 0.3.5.

It assumes the interim merge was a true merge commit (not squash, not rebase) and that nothing else has landed on `main` since. If either is not true, stop and work out a plan first.

1. **Make the undo.** Start with `git fetch origin`. Then start a new branch from the current `main` and revert the alpha's merge commit, keeping the first parent: `git switch -c revert/v2.0-alpha origin/main`, then `git revert -m 1 <merge-commit> --no-edit`. The files on the branch are then exactly what `main` held before the merge (0.3.5, commit 817cf24); `git diff 817cf24 HEAD` prints nothing.
2. **Change the version number.** Set the version to `0.3.6` in both plugin manifests (`.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`) and in `tests/test_pack.py` (`VERSION = "0.3.6"`; the 0.3.5 test suite pins the version, so the tests fail if you skip it). Add a CHANGELOG entry `## 0.3.6`: "Reverts the v2.0 alpha on main; identical to 0.3.5." Commit. The number must change. The app decides whether to refresh its copy from the version number, so putting back `0.3.5` would leave anyone who already updated stuck on the alpha.
3. **Merge the undo.** `main` at 0.3.5 has no `.github/` folder, so no automatic tests run on this pull request. Run the tests yourself on the revert branch (`python -m pytest tests -q`; expect `308 passed`), push the branch, open a pull request and paste the test result into it. Merge it with a merge commit (not squash, not rebase). Tag the result `v0.3.6`, push the tag, and post a comment on issue #1.
4. **Users update.** Anyone who updates the marketplace now gets 0.3.6, which behaves exactly like 0.3.5. Anyone who pinned `#v0.3.5` is unaffected.
5. **Bringing v2.0 back later.** On the feature branch, note its tip first (`git rev-parse HEAD`; call it `<feature-tip-before>`). Bring in `main` (which now contains the undo), then revert the undo commit itself (`git merge origin/main`, then `git revert <undo-commit>`). Expect conflicts on the two manifests, the CHANGELOG and the `VERSION` line in `tests/test_pack.py`: keep the feature branch's version of each. Then check that `git diff <feature-tip-before> HEAD` shows only the lines you meant to change. Skipping this step would make the next merge silently drop all of v2.0.
